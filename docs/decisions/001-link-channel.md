# 001. Канал «фон → состояние» без async-рантайма

## Решение

`src/task.rs`: `link::<S>()`, `Link::send(FnOnce(&mut S) + Send)`, `spawn`, `Task`, `sleep`, `Ui::pump`.
Без зависимостей и без tokio/async-std: ядро остаётся лёгким.

- Очередь замыканий лежит в `thread_local` UI-потока (`INBOX`); `Link` держит `Arc` на неё. `S` не обязан
  быть `Send`: между потоками ходят только замыкания.
- Waker хранится в очереди своего потока, поэтому `set_waker` зовут на UI-потоке (раннер в `app.rs` так и делает).
- Одно пробуждение на пачку `send`: флаг `woken` сбрасывает `pump`, цикл будится один раз, а не на каждое слово.
- `Ui::frame` первым делом зовёт `pump`; применённое обновление = кадр по делу, в простое 0% CPU.
- Отмена = drop `Task`. Обновления отменённого `Link` отбрасываются и при `send`, и при `pump`.
  На native `cancel()` делает `unpark` рабочего потока, так что `sleep` прерывается сразу.
- `after()` остался для таймеров на UI-потоке: ему не нужны потоки.
- Native: каждый `spawn` — свой поток, поэтому будущее может блокироваться (синхронный HTTP) и не обязано быть `Send`.
  Wasm: `spawn` отдаёт будущее исполнителю из `set_spawner` (`app.rs` ставит `spawn_local`).

## Ограничения

- Блокирующее чтение не прерывается: отмена заметна только со следующего чанка.
- На wasm отмена срабатывает при следующем poll будущего.
- `sleep` на wasm (через `setTimeout`) есть только с фичей `app`.
- Клиентам, которым нужен tokio, нужен свой рантайм: наши потоки его не дают.
  Рекомендация: `ureq` на native, `fetch` на web.
- `link()` на потоке без `Ui` молча теряет обновления: его очередь никто не качает.
